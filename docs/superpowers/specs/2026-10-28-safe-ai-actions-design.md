# 안전한 AI 실행 파이프라인 1단계 설계 — "AI가 계획하고, 사람이 승인하고, 좁은 권한으로 실행"

- 작성일: 2026-10-28
- 사용자 결정
  - 사용자가 붙여 준 설계안("① 안전한 AI 실행 파이프라인")을 하기로 했다.
  - 1단계만 먼저 한다. 되돌릴 수 있는 작업만 다룬다.
  - 질문 단계는 "기본값으로 ㄱㄱ"로 건너뛰었다. 그래서 아래 **기본값은 모두 내가 정한 것**이다.
- 바탕
  - `src/lib/slack-control/`: 규칙 기반 EC2 켜기·끄기, 2단계 승인, 감사 로그(ADR-010).
  - `src/lib/slack-chatops/`: Slack 봇.
  - `src/lib/ai/`: Bedrock 호출.

## 1. 왜 만드는가
- 지금 AWSops가 AWS를 바꾸는 길은 Slack 제어 하나뿐이다. EC2 켜기·끄기·재부팅만 되고, 명령도 규칙으로만 알아듣는다.
- 그래서 "web-dev에 owner=jiwoo 태그 붙이고 8080 포트 우리 사무실 IP만 열어 줘" 같은 말은 처리하지 못한다.
- AI에게 AWS를 직접 맡기면 위험하다.
  - 2026-10-26 점검에서 AI 도구가 리소스를 끄거나 지울 수 있다는 걸 발견했다. 그래서 읽기 전용으로 잠갔다.
  - AWS에는 범용 dry-run이 없다. EC2 `DryRun`도 권한만 확인할 뿐, 무엇이 바뀌는지는 보여 주지 않는다.
- 그래서 AI는 **계획(JSON)만** 만든다. 실제 실행은 AI 밖에서 정해진 순서로 한다: 검사 → 미리 보기 → 사람 2명 승인 → 계획에 적힌 것만 허용하는 15분짜리 권한으로 실행.

## 2. 목표 / 비목표 / 반목표
- **목표 (1단계)**
  - Slack에서 자연어로 요청하면 AI가 **ActionPlan**을 만든다.
  - 백엔드는 이 계획을 다음 순서로 처리한다.
    1. 형식 검사
    2. 대상 확정(규칙 기반)
    3. 현재 상태 스냅샷
    4. 규칙 검사
    5. 영향 범위 계산(간단 버전)
    6. 미리 보기(바뀌기 전 → 후)
    7. 권한 미리 확인(DryRun)
    8. 2단계 승인
    9. 세션 정책으로 좁힌 임시 권한으로 실행
    10. 해시 체인 감사 로그
    11. 되돌리기 버튼
  - 지원 작업은 6가지이고, 모두 되돌릴 수 있다.
    - `ec2.start`, `ec2.stop`
    - `tag.set`: 태그 추가 또는 값 변경
    - `tag.remove`
    - `sg.ingress.add`, `sg.ingress.remove`
  - 대상 리소스 종류는 EC2 인스턴스와 보안그룹이다.
- **비목표 (2단계 이후)**
  - 대시보드 화면: 계획·감사 기록 보기, 화면에서 승인하기.
  - Cedar/OPA 정책 엔진. 1단계는 TypeScript 규칙으로 한다.
  - 의존성 그래프 기반 영향 범위.
  - S3 Object Lock 감사 저장소.
  - 삭제·생성 작업, RDS, 스케일링, 재부팅. 재부팅은 기존 Slack 제어가 계속 담당한다.
  - 다른 계정과 다른 리전. 1단계는 호스트 계정의 `ap-northeast-2`만 다룬다.
  - 기존 Slack 제어(`slack-control`)를 이 파이프라인으로 합치는 일.
- **반목표 (이렇게 되면 실패)**
  - 사람 두 명(요청자 확인 + 다른 승인자 승인)을 거치지 않고 AWS가 바뀐다.
  - 리소스의 태그, 이름, 로그, 봇 답변 같은 **데이터 내용이 무엇을 실행할지에 영향을 준다** (프롬프트 인젝션).
  - 실제로 실행된 API 호출이 미리 보기에서 보여 준 것과 다르다.
  - 되돌리기가 그 사이 다른 사람이 바꾼 내용을 아무 말 없이 덮어쓴다.
  - 감사 로그 한 줄을 고치거나 지워도 아무도 알아채지 못한다.
  - `awsops:control=allow` 태그가 없는 리소스, 그러니까 다른 팀 리소스가 바뀐다.
  - 이 기능이 일반 질문("포트 여는 방법 알려줘")을 가로챈다.

## 3. 기본값 (내가 정함)

### 3.1 들어오는 길
- Slack 멘션만 받는다. 라우팅 순서는 `control`(기존 규칙 기반 켜기·끄기) → **`action-plan`(신규)** → change → cost → AI다.
- 감지(`detectActionIntent`)는 규칙으로 한다.
  - 다음 두 가지가 함께 있어야 한다.
    - 명령형 동사: 붙여/달아/바꿔/변경해/지워/떼/삭제해/추가해/열어/닫아/막아/허용해 + 줘·주세요·라
    - 대상 단어: 태그/보안그룹/sg-/포트/인바운드/규칙
  - 방법을 묻거나 가정하는 질문("방법", "어떻게", "할 수 있어?", "하면 돼?")은 제외한다.
  - 감지되지 않으면 아무 비용 없이 다음 단계로 넘어간다.
- 켜기·끄기만 있는 말("web-dev 꺼줘")은 기존 `slack-control`이 먼저 가져간다. 동작은 그대로다.
- 켜기·끄기가 태그나 보안그룹 작업과 섞인 말은 action-plan이 받아야 한다. 그러려면 `slack-control`이 action-plan 감지에 걸리는 문장은 건너뛰어야 한다. 이 조건 하나만 추가하고, `actionPlan.enabled === true`일 때만 적용한다. 꺼져 있으면 `slack-control` 동작이 지금과 완전히 같다. (빌더 확인 후 내가 정함)

### 3.2 계획을 짜는 AI (플래너)
- Bedrock 모델은 `getBedrockModelId()`로 정한다. 강제 tool 호출(`tool_choice: {type:'tool', name:'submit_plan'}`)로 JSON을 받는다. 타임아웃은 30초다.
- **플래너가 받는 것은 딱 두 가지다.**
  1. 요청자의 이번 메시지 원문(멘션 제거, 최대 1000자)
  2. 작업 목록 설명(고정 텍스트)과 출처 별칭 이름 목록(관리자 설정)
- 스레드 이전 대화, 리소스 목록, 이름, 태그 값, 보안그룹 설명, 로그는 **절대 주지 않는다.** CaMeL 논문의 "특권 플래너는 신뢰할 수 없는 데이터를 보지 않는다"를 단순화한 것이다.
- 플래너 출력 스키마(`submit_plan`)는 세 가지 중 하나다.
  - `{ kind: 'plan', steps: Step[], summary: string }`. 단계는 최대 5개다.
  - `{ kind: 'clarify', question: string }`: 무엇을 할지 모호할 때. 1단계에서는 이어서 답하는 대화를 받지 않는다. 안내 문구에 "처음부터 한 문장으로 다시 써 주세요(예: …)"를 붙여서, 사용자가 요청 전체를 다시 쓰게 한다. 3.3에서 대상이 모호할 때도 똑같이 처리한다. (빌더 확인 후 내가 정함)
  - `{ kind: 'not-action' }`: 실행 요청이 아닐 때. 이 경우 AI 답변 경로로 넘긴다.
- `Step`은 `{ action, target: { ref: string }, params }`다.
  - `ref`는 사용자가 말한 이름이나 ID를 **그대로 옮긴 문자열**이다. 플래너는 리소스를 모르기 때문에, 대상 확정은 3.3의 코드가 한다.
  - `params`
    - `tag.set`: `{ key, value }`
    - `tag.remove`: `{ key }`
    - `sg.ingress.add` / `sg.ingress.remove`: `{ protocol: 'tcp'|'udp', fromPort, toPort, source }`
      - `source`는 IPv4/IPv6 CIDR이거나, `sg-...`이거나, `alias:<이름>`이다.
      - **출처 별칭**(빌더 확인 후 내가 정함): 관리자가 `config.actionPlan.sourceAliases`(예: `{"사무실": ["203.0.113.0/24"]}`)에 미리 적어 둔 이름이다. "사무실 IP" 같은 말을 처리하려고 둔다. 관리자가 쓴 설정이라 신뢰할 수 있는 입력이고, 그래서 플래너에게 **별칭 이름 목록만** 준다(CIDR 값은 주지 않는다). 별칭 하나가 CIDR 여러 개면 단계도 CIDR마다 하나씩 펼친다. 이렇게 펼친 단계도 `maxSteps`에 센다. 모르는 이름이면 `clarify`로 답한다.
      - `add`일 때는 `description?`를 받을 수 있다.
    - `ec2.start` / `ec2.stop`: 비어 있다.
  - `summary`와 `question`은 표시용이다. 실행에는 쓰지 않고, Slack에 넣기 전에 `safeName` 수준으로 정리한다.
- 플래너가 실패하면(시간 초과, 형식 오류) "계획을 만들지 못했어요"라고 답하고 끝낸다. 일반 AI로 넘기지 않는다.

### 3.3 형식 검사와 대상 확정 (코드, LLM 없음)
- 형식 검사는 손으로 짠 검증 함수로 한다. 새 의존성은 넣지 않는다.
  - 알 수 없는 action이나 필드는 거부한다.
  - 포트는 0–65535이고 from ≤ to여야 한다.
  - CIDR 형식이 맞아야 한다.
  - 태그 키는 1–128자, 값은 0–256자다. 키가 `aws:`로 시작하면 거부한다.
  - 하나라도 틀리면 계획 전체를 거부한다.
- 대상 확정
  - 후보는 **`awsops:control=allow` 태그가 붙은** EC2 인스턴스(종료된 것 제외)와 보안그룹이다.
  - `ref`가 `i-…`나 `sg-…`면 ID로 정확히 찾는다.
  - 그 밖에는 Name 태그(보안그룹은 GroupName도)를 단어 단위로 맞춘다. `slack-control/parse.ts`와 같은 방식이다.
  - EC2 작업은 인스턴스, `sg.*` 작업은 보안그룹에서 찾는다. 태그 작업은 둘 다에서 찾는다.
  - **`sg.*` 작업의 대상으로 서버를 말한 경우**(예: "web-dev 8080 열어줘"), 그 서버에 붙은 보안그룹을 대상으로 삼는다. 단, 그 보안그룹이 **딱 하나이고 그 SG에도 허용 태그가 있을 때만** 그렇게 한다. 여러 개면 후보 SG 목록을 보여 주고 다시 써 달라고 안내한다. 영향 범위는 그 SG를 기준으로 계산하므로, 다른 서버가 같은 SG를 쓰면 카드에 그 서버들도 나온다. (빌더 확인 후 내가 정함)
  - 못 찾거나 후보가 여러 개면 계획을 멈추고, 후보 목록과 함께 다시 말해 달라고 안내한다.
  - 계획 하나가 건드리는 리소스는 최대 3개다.

### 3.4 스냅샷
- 대상마다 지금 상태를 다시 읽는다.
  - 인스턴스: 상태와 태그
  - 보안그룹: 태그와 인바운드 규칙 전체(`DescribeSecurityGroupRules`)
  - 보안그룹의 영향 범위: 그 SG를 쓰는 ENI와 ENI에 붙은 인스턴스(`DescribeNetworkInterfaces`, `group-id` 필터)
- 단계마다 바뀌기 전과 후를 계산한다. **이미 원하는 상태인 단계**는 빼고 "이미 되어 있음"으로 표시한다. 예: 태그가 이미 그 값이거나, 같은 규칙이 이미 있거나, 이미 꺼져 있는 경우.
  - 모든 단계가 빠지면 "바꿀 게 없어요"라고 답하고 끝낸다.
- `sg.ingress.remove`는 맞는 규칙을 `SecurityGroupRuleId`로 확정한다. 프로토콜, 포트, 출처가 모두 같아야 한다. 없으면 "그런 규칙이 없어요"로 거부한다.

### 3.5 규칙 검사 (`policy.ts`, 순수 함수)
- 하나라도 거부되면 계획 전체를 실행하지 않는다. 일부만 실행하지 않는다. 거부 이유는 모두 보여 준다.
- 규칙
  1. 대상에 `awsops:control=allow` 태그가 없으면 거부한다. 3.3에서 걸러지지만 한 번 더 확인한다.
  2. **운영 리소스 보호**: 태그 `env`/`Environment`/`environment` 값이 `prod`/`production`이면 그 리소스의 모든 단계를 거부한다. 운영 표시 태그를 지우는 것도 막힌다.
  3. **태그 키 보호**: `awsops:`로 시작하는 키는 만들거나 바꾸거나 지울 수 없다. 제어 허용 태그를 스스로 늘리는 것을 막기 위해서다.
  4. **전체 공개 금지**: 출처가 `0.0.0.0/0`이나 `::/0`인 `sg.ingress.add`는 포트 범위가 정확히 80 또는 443일 때만 허용한다.
  5. **넓은 범위 금지**: 프로토콜 `-1`(전체), 포트 범위 1000개 초과는 거부한다.
  6. **영향 범위 상한**: 보안그룹 변경은 그 SG를 쓰는 ENI가 `maxBlastRadius`(기본 5)를 넘으면 거부한다. "영향이 너무 커서 콘솔에서 직접 해 주세요"라고 안내한다.
  7. 상태와 맞지 않는 작업은 거부한다. 기준은 이렇다.
     - 이미 목표 상태면(꺼진 서버를 끄라) 거부가 아니라 3.4처럼 "이미 되어 있음"으로 **제외**한다.
     - 중간 상태면 **거부**한다. `stopping`인 서버에 `ec2.start`, `pending`인 서버에 `ec2.stop`, 그리고 `shutting-down`인 서버가 여기에 해당한다. (빌더 확인 후 내가 정함)

### 3.6 미리 보기 카드
기존 Slack 제어 카드와 같은 모양이고, 한 요청에 카드 하나를 두고 상태가 바뀔 때마다 다시 그린다. 카드에 들어가는 내용:
- 요청 원문(인용, 200자)과 요청자
- 단계마다 한 줄씩, 바뀌기 전 → 후
  - 예: `web-dev (i-0abc…) · 태그 owner: (없음) → jiwoo`
  - 예: `sg-web (sg-0123…) · 인바운드 추가 tcp 8080 ← 203.0.113.0/24`
- "이미 되어 있음"으로 뺀 단계
- 영향 범위
  - 보안그룹: "이 보안그룹을 쓰는 서버 2대: a, b"
  - 인스턴스 끄기: "서버 1대가 꺼져요"
- 규칙 검사 결과와 권한 미리 확인 결과
- "되돌릴 수 있어요(24시간 안)" 표시
- 버튼: 1단계 확인과 취소, 2단계 최종 승인과 거절. 최종 승인은 Slack confirm 대화상자를 거친다.

이름과 태그 값은 모두 `safeName`으로 정리한다. 태그 값과 SG 설명은 표시만 하고, 다른 어디에도 쓰지 않는다.

### 3.7 권한 미리 확인 (DryRun)
- 미리 보기를 만들 때 실행 역할을 세션 정책과 함께 맡는다. 이때 SourceIdentity는 `slack-<요청자>`다.
- 그 상태로 단계마다 `DryRun: true` 호출을 한다. `DryRunOperation` 응답이 오면 통과이고, `UnauthorizedOperation`이 오면 거부다.
- 거부되면 이렇게 안내한다: "실행 권한이 없어요 — 관리자가 `scripts/17-setup-action-executor.sh`에 이 리소스를 등록해야 해요."

### 3.8 승인
- `slack-control`과 **같은 2단계 규칙**을 쓴다. 승인자 목록, 본인 승인 금지, TTL 15분, 1회 실행, 메모리 보관도 같다.
- 승인자 설정도 `config.slackControl`을 함께 쓴다(`approverIds`, `allowSelfApproval`, `requestTtlMinutes`).
- 권한 규칙이 한 곳에만 있도록 `slack-control/requests.ts`의 상태 기계를 일반화해서 두 기능이 같이 쓴다. 기존 테스트는 그대로 통과해야 한다.

### 3.9 실행
- 최종 승인이 나면 실행 직전에 **스냅샷을 다시 읽는다.**
  - 계획을 만들 때와 대상 상태가 하나라도 다르면 실행하지 않는다. "그 사이 상태가 바뀌었어요, 다시 요청해 주세요"라고 안내한다.
  - 비교 대상은 인스턴스 상태, 관련 태그 값, 관련 SG 규칙의 존재 여부다.
- 실행 역할 `AWSopsActionExecutorRole`을 다음 조건으로 맡는다.
  - `SourceIdentity=slack-<승인자>`
  - `DurationSeconds: 900`
  - **인라인 세션 정책**: 이 계획의 단계에 필요한 API 액션과 정확한 리소스 ARN만 허용한다.
- 단계는 계획 순서대로 하나씩 실행한다.
  - 실패하면 그 자리에서 멈춘다. 자동 롤백은 하지 않는다.
  - 카드에는 성공한 단계, 실패한 단계, 실행하지 않은 단계를 나눠 보여 준다. 성공한 단계는 되돌리기 대상이 된다.
- 단계마다 AWS 응답의 `$metadata.requestId`를 기록한다. CloudTrail 이벤트의 `requestID`와 맞춰 볼 수 있다.

### 3.10 감사 로그
- 파일은 `data/action-plan/audit.jsonl`이고, 추가만 한다. 경로는 `ACTION_PLAN_DATA_DIR`로 바꿀 수 있다.
- 줄마다 `prevHash`와 `hash`를 둔다. `hash = sha256(prevHash + 이 줄의 정렬된 JSON)`이고, 첫 줄의 prevHash는 `"0"`이다.
- `verifyAuditChain(file)`은 `{ ok: true } | { ok: false, brokenAt: 줄번호 }`를 돌려준다. 단위 테스트로 위변조를 잡는지 확인한다.
- 기록하는 시점은 상태가 바뀔 때마다다: 생성, 확인, 승인, 거절, 취소, 만료, 실행 결과, 되돌리기 요청.
- 기록하는 내용
  - 요청 원문(1000자)
  - 플래너 출력 원본
  - 확정된 계획
  - 규칙 검사 결과
  - 요청자와 승인자 ID
  - 단계별 결과와 requestId
- 계획 안의 CIDR은 무엇을 열었는지 보여 주는 핵심 내용이라 그대로 기록한다. 자격 증명과 토큰은 기록하지 않는다. AWS 응답 본문도 requestId와 규칙 ID 말고는 기록하지 않는다.
- 쓰기에 실패해도 승인 흐름은 막지 않고 경고 로그만 남긴다. `slack-control` 감사와 같은 원칙이다.
- 진짜로 고칠 수 없는 저장소(S3 Object Lock)는 2단계에서 한다.

### 3.11 되돌리기
- 실행할 때 단계마다 **역연산을 코드로 계산해서** 저장한다. LLM은 쓰지 않는다. 저장 위치는 `data/action-plan/executions/<id>.json`이다.

  | 실행한 작업 | 역연산 |
  |---|---|
  | `ec2.stop` | `ec2.start` |
  | `ec2.start` | `ec2.stop` |
  | 새 태그 추가 | `tag.remove` |
  | 태그 값 변경 | 이전 값으로 `tag.set` |
  | `tag.remove` | 이전 값으로 `tag.set` |
  | 규칙 추가 | Authorize 응답의 규칙 ID로 `sg.ingress.remove` |
  | 규칙 삭제 | 저장해 둔 원래 규칙(설명 포함)으로 `sg.ingress.add` |

- 결과 카드에 "↩️ 되돌리기" 버튼을 둔다. 실행 후 24시간(`undoHours`) 동안 보인다.
  - 누르면 역연산 계획으로 **새 요청**을 만든다. 누른 사람이 요청자가 되고, 3.4–3.9를 똑같이 거친다(검사, 미리 보기, 2단계 승인).
- **덮어쓰기 방지**: 되돌리기 스냅샷에서 현재 상태가 "실행 직후 상태"와 다른 단계는 빼고 "그 사이 다른 변경이 있어서 되돌리지 않아요"로 표시한다.
- 되돌리기를 다시 되돌리는 것도 같은 방식으로 된다.

### 3.12 IAM (`scripts/17-setup-action-executor.sh`)
- 새 역할 `AWSopsActionExecutorRole`을 만든다. 신뢰 정책은 16번 스크립트와 같은 형태다: `awsops-ec2-role`만 맡을 수 있고, `sts:SourceIdentity`가 `slack-*`여야 한다.
- 인자로 받은 인스턴스 ID와 보안그룹 ID 목록에만 권한을 준다.
  - 목록에 있으면서 `aws:ResourceTag/awsops:control=allow`인 리소스에만 허용한다.
  - 허용 액션: `ec2:StartInstances`, `ec2:StopInstances`, `ec2:CreateTags`, `ec2:DeleteTags`, `ec2:AuthorizeSecurityGroupIngress`, `ec2:RevokeSecurityGroupIngress`
  - 별도 Deny: `aws:TagKeys`에 `awsops:*`가 있는 CreateTags/DeleteTags
- 사용법: `bash scripts/17-setup-action-executor.sh i-xxx sg-yyy ...`. ID 없이 실행하면 권한을 모두 지운다.
- 이 스크립트를 실행하는 것은 IAM 변경이라 **사용자 승인 후에** 한다. 빌드할 때는 스크립트만 만든다.

### 3.13 설정 (`data/config.json`)
```json
"actionPlan": { "enabled": false, "maxSteps": 5, "maxResources": 3, "maxBlastRadius": 5, "undoHours": 24, "sourceAliases": {} }
```
- `enabled === true`이고 `slackControl.approverIds`가 있어야 켜진다.
- 꺼져 있으면 감지된 요청에 "AI 실행 기능이 꺼져 있어요"라고 한 줄 답한다. 플래너는 호출하지 않는다.

### 3.14 결정 기록
- ADR-011 "AI 계획 + 결정적 실행"을 새로 쓴다.
- ADR-010은 "제어 명령 해석에 LLM 금지"라고 했다. 이번에 LLM을 **제안자**로 들이는 이유와, 그래도 안전한 이유를 적는다.
  - 플래너는 데이터를 보지 않는다.
  - 대상은 코드가 확정한다.
  - 규칙과 IAM이 최종 경계다.
  - 사람 2명이 승인한다.
- ADR-010의 신뢰 경계(호스트 셸 = 제어 권한)도 그대로 이어받는다고 적는다.

## 4. 제약
- 앱 규칙
  - fetch는 `/api/*`를 쓴다.
  - 컴포넌트는 default export로 둔다. 1단계에는 화면이 없다.
  - 오류 메시지에는 오류 이름만 넣는다.
  - `data/`는 gitignore돼 있다.
- 테스트(vitest)는 AWS와 Bedrock을 가짜로 대신한다. 실제 AWS를 호출하는 테스트는 없다.
- 기존 동작은 바뀌면 안 된다: `slack-control` 켜기·끄기, 변경 질문, 비용 질문, AI 답변. 기존 테스트가 모두 통과해야 한다.
- **공유 계정이다.** 실제 동작 확인에는 태그 붙은 테스트 인스턴스와 보안그룹, 그리고 17번 스크립트 실행이 필요하다. 전부 리소스 생성 또는 IAM 변경이라 사용자 승인을 받고 한다. 배포는 `actionPlan.enabled: false` 상태로 한다.
- AI 답변 도구는 계속 읽기 전용이다. 이 파이프라인은 AI 도구(MCP/Lambda)와 완전히 별개다.
- 조회와 실행 모두 대시보드 프로세스의 AWS SDK로 한다. 리전은 `ap-northeast-2`이고, 호출 하나의 타임아웃은 15초다.

## 5. 빌더에게 맡기는 것
- 파일 나누기. 예: `src/lib/action-plan/{types,detect,planner,validate,resolve,snapshot,policy,preview,permissions,execute,undo,audit,cards,handle}.ts`. `src/lib/action-plan/CLAUDE.md`도 함께 둔다.
- 감지 정규식의 세부 내용. 3.1의 포함·제외 예시가 테스트로 들어가면 된다.
- 카드 문구의 세부 표현. 쉬운 한국어로 쓴다.
- `requests.ts`를 일반화하는 구체적인 방식. 제네릭으로 할지 payload 필드로 할지.
- 세션 정책 JSON을 어떻게 만들지. AWS 액션별 필수 리소스 타입(예: AuthorizeSecurityGroupIngress의 `security-group-rule`)은 AWS 서비스 권한 문서에 맞추고, 그 내용을 테스트로 고정한다.
